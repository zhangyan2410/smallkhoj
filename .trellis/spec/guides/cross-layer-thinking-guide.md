# Cross-Layer Thinking Guide

> **Purpose**: Think through data flow across layers before implementing.

---

## The Problem

**Most bugs happen at layer boundaries**, not within layers.

Common cross-layer bugs:
- API returns format A, frontend expects format B
- Database stores X, service transforms to Y, but loses data
- Multiple layers implement the same logic differently

---

## Before Implementing Cross-Layer Features

### Step 1: Map the Data Flow

Draw out how data moves:

```
Source → Transform → Store → Retrieve → Transform → Display
```

For each arrow, ask:
- What format is the data in?
- What could go wrong?
- Who is responsible for validation?

### Step 2: Identify Boundaries

| Boundary | Common Issues |
|----------|---------------|
| API ↔ Service | Type mismatches, missing fields |
| Service ↔ Database | Format conversions, null handling |
| Backend ↔ Frontend | Serialization, date formats |
| Component ↔ Component | Props shape changes |

### Step 3: Define Contracts

For each boundary:
- What is the exact input format?
- What is the exact output format?
- What errors can occur?

---

## Common Cross-Layer Mistakes

### Mistake 1: Implicit Format Assumptions

**Bad**: Assuming date format without checking

**Good**: Explicit format conversion at boundaries

### Mistake 2: Scattered Validation

**Bad**: Validating the same thing in multiple layers

**Good**: Validate once at the entry point

### Mistake 3: Leaky Abstractions

**Bad**: Component knows about database schema

**Good**: Each layer only knows its neighbors

---

## Checklist for Cross-Layer Features

Before implementation:
- [ ] Mapped the complete data flow
- [ ] Identified all layer boundaries
- [ ] Defined format at each boundary
- [ ] Decided where validation happens

After implementation:
- [ ] Tested with edge cases (null, empty, invalid)
- [ ] Verified error handling at each boundary
- [ ] Checked data survives round-trip

## Cross-Platform Template Consistency

The same Trellis command/skill exists in **multiple platform surfaces** in this repo — e.g. `trellis-check` ships as a command (`.zcode/commands/trellis/check.md`), a skill body (`.agents/skills/trellis-check/SKILL.md`), a Claude copy (`.claude/skills/trellis-check/SKILL.md`), and a Codex subagent (`.codex/agents/trellis-check.toml`). Shared hooks are also multi-copy: `inject-workflow-state.py` / `session-start.py` are written into every hook-capable platform dir (`.claude/hooks/`, `.codex/hooks/`, ...). Changing one copy is a cross-layer boundary.

### Checklist: After Modifying Any Command/Skill/Hook Template

- [ ] Find all platform copies first: `find .zcode .agents .claude .codex -name '<name>*'`
- [ ] Update every copy, adapting per-platform form (Markdown `.md` vs Codex TOML subagent; the `.codex` variant documents that Codex does NOT auto-inject task context and must run `task.py current` itself)
- [ ] Respect managed blocks: content inside `<!-- TRELLIS:START/END -->` (AGENTS.md) or `<comet-ambient-resume>` is overwritten by `trellis update` / `comet init` — durable edits go outside the block or into the generating tool
- [ ] Coverage is intentionally uneven — `.zcode/commands/trellis/` has 12 commands while `.claude/commands/trellis/` has 2 ("Not every platform exposes every command", AGENTS.md). When adding a command, decide per platform whether it mounts.

**Real drift example (live in this repo)**: the shared hook `inject-workflow-state.py` has already diverged between `.claude/hooks/` and `.codex/hooks/` — the `.codex` copy contains an extra `ZCODE_PROJECT_DIR` mapping and a `.zcode` script-dir branch that `.claude` lacks. Treat "sync platform hook copies" as its own explicit change; never assume copies are identical.

## Generated Runtime Template Upgrade Consistency

Some generated files are both documentation and runtime input. In this repo, `.trellis/workflow.md` is parsed by `.trellis/scripts/common/workflow_phase.py` (`_MARKER_RE` platform tags), the platform `session-start.py` hooks (regex over `[workflow-state:*]` blocks + TOC), and `get_context.py --mode phase --platform <p>` (via `common/git_context.py`). Managed blocks in `AGENTS.md`/`CLAUDE.md` are regenerated by `trellis update`. Template changes must be validated against what every parser reads, not just what the file looks like.

### Checklist: After Modifying A Runtime-Parsed Template

- [ ] Identify every parser that reads the template — for `workflow.md`: `workflow_phase.py` (platform marker lines), `session-start.py` hooks (`[workflow-state:*]` tags + TOC), `get_context.py --platform` filtering
- [ ] Check whether load-bearing syntax lives outside managed regions — platform marker lines like `[Claude Code, Cursor, OpenCode, codex-sub-agent]` / `[codex-inline, Kilo, Antigravity, Devin]` (workflow.md) are parsed but sit in no protected block; `trellis update` only rewrites managed blocks and leaves stale markers in place
- [ ] The `[workflow-state:STATUS]` breadcrumb tags are the SINGLE source of truth for hooks — since v0.5.0-rc.0 the hook scripts have no fallback dict (workflow.md "WORKFLOW-STATE BREADCRUMB CONTRACT"); renaming a tag silently degrades every platform hook to the generic hint line
- [ ] Verify with `get_context.py --mode phase --step <X.Y> --platform <p>` for each platform touched (the pattern `.agents/skills/trellis-continue` documents)
- [ ] Update the spec or task doc that owns the runtime contract

**Real-world example (contract note)**: AGENTS.md states edits inside the `TRELLIS:START/END` block "may be overwritten by a future `trellis update`" — hand-tuned routing text placed inside the block survives only until the next update; keep platform behavior fixes outside managed blocks or in the generating tool.

## Mode-Detection Probe Checklist

When code picks a mode/endpoint by probing (port connect, binary lookup, CLI JSON status), the probe quality decides correctness. In this repo: the dashboard's `_collect_agents` probes the DSH web port with a 0.2s socket connect and `shutil.which` for the binary (`tools/trellis-dashboard/collector.py`); `agent_runner._resolve_dsh_bin` resolves env override > `~/.dsh/toolchain/bin/dsh` wrapper > PATH; the Comet resume probe routes session entry via `comet resume-probe . --stdin --json` (AGENTS.md `<comet-ambient-resume>` block).

### Before implementing:
- [ ] Probe runs in **ALL** code paths that use the result (interactive, scripted, delegated-agent prompts)
- [ ] "Not present" vs transient error are distinguished — don't treat both as absent
- [ ] Transient errors **abort or retry with a reported reason**, never silently switch modes
- [ ] Probe failure produces an explicit, shaped fallback (e.g. the collector returns `{"sdkAvailable": false, "busy": false, "messages": []}` instead of raising)
- [ ] Resolution ladders (env > wrapper > PATH) are documented where they're implemented, not in callers' heads

### After implementing:
- [ ] Trace every path from probe result to the decision branch — no fallthrough
- [ ] For router probes, only trust the fields the contract declares: resume-probe results are trusted for `workflow`/`skill`/`entrySource` only; on invalid state without a `nextCommand`, STOP and report — never guess another workflow
- [ ] External format contracts (CLI JSON envelopes, marker formats) are schema-checked; non-JSON, non-zero-exit, or wrong-schema output means "stop and report the error verbatim", not "fall back"
- [ ] Probe consumers that read structured responses parse the COMPLETE body, never a fixed-size prefix

**Real-world example (this repo)**: the comet entry skill resolves `comet workflow resolve . --activate --json` and treats missing CLI / non-zero exit / non-JSON / invalid schema as a hard stop with the original error — no fallback guessing. The dashboard agent panel applies the same discipline: if `chat_status` raises, it degrades to an explicit `sdkAvailable: false` payload rather than pretending the service is up.

## When to Create Flow Documentation

Create a dedicated flow doc under `docs/` when:
- The feature spans 3+ layers (frontend → backend → daemon/runtime, or control-plane state)
- It changes browser-visible product behavior, daemon/runtime delivery, or control-plane state (the trigger declared by `docs/real-test-sop-template.md`)
- The verification path is easy to fake and needs a "Do Not Use" anti-list (see `docs/real-runtime-dm-reply-sop.md`: no fake-recorder, no direct DB inserts, no manual agent-reply POSTs)
- The area has caused repeat bugs (orphan daemons → `docs/orphan-daemon-cleanup.md`; P2 LAN registration → `docs/p2-lan-daemon-registration-runbook.md`)

Rules that make flow docs work here:
- Give the doc a machine-checkable evidence format (the SOP template's `REAL_<task-slug>_<yyyyMMddHHmmss>` marker) instead of prose-only claims.
- Mount it in an index agents actually read: the AGENTS.md Project Index routes UI acceptance to `./twd`, real-test environment selection to the `smallkhoj-real-test` skill (whose read-only context-collector output must be embedded verbatim in delegated prompts), and multi-agent Git flow to `docs/multi-agent-development-workflow.md`. An unindexed flow doc does not exist for an agent.
- Layer SOPs instead of duplicating: deeper-path docs (real-runtime DM reply) build on the generic template's marker discipline.
