## Cross-layer data flow

Browser click on Files tab → `setActiveTab("files")` in client state → `useEffect` in `channel-client.tsx:238-241` calls `refreshFiles()` → `apiGet<{files: FileItem[]; count: number}>('/api/v1/files?channelId=...')` → Next.js `/api` proxy → backend `public_api.py:1371-1393` → `SELECT * FROM file_entries WHERE server_id=... AND channel_id=...` → returns serialized file list → UI renders cards. The data flow for an upload would need: `POST /api/v1/files` (multipart) → `FileEntry` insert → `GET /api/v1/files` returns the new row → Files tab card appears. The first half of that flow is missing.

## Known gaps / opportunities

* **The public upload endpoint is missing.** This is the central PRD gap. The implementation has the read side (Files tab renders existing files), the disabled affordances (composer attach buttons), and the source-message-link handler. The write side is the blocker. Recommend opening `.trellis/tasks/06-09-public-file-upload-endpoint` (or adding to the current task's check.jsonl) with a stub endpoint spec: `POST /api/v1/files` accepting `multipart/form-data` (file + optional `channelId`, `messageId`), gate with browser session auth (`X-Account-Token` + `X-Public-Key`), call the same `FileEntry` insert path that `agent_api.upload_attachment` already uses (`agent_api.py:3007-3030`), enforce a server-side size cap and MIME allowlist, then re-render the Files tab.
* **No child Trellis task for the upload gap.** The PRD explicitly says "If backend upload is incomplete, document exact API/model gaps as child follow-up." Kimi's notes mention the gap but the directory has no follow-up task. Even a placeholder `06-09-public-file-upload-endpoint/prd.md` (Goal: enable browser-session file upload; Acceptance: POST /api/v1/files accepts multipart and persists a FileEntry visible in GET /api/v1/files) would satisfy this.
* **No file type / size validation on the server side.** `agent_api.upload_attachment` writes any bytes to disk with no MIME check or size cap (`agent_api.py:3007-3016`). If a public upload endpoint is added, it should reject dangerous types and cap size — and the UI should show the error from the server (currently the Forms/actions have no error-toast pattern in `channel-client.tsx` for file uploads since they don't exist).
* **Source message link is unverified end-to-end** because there are zero files in the system. The handler is straightforward (`setActiveTab("chat")` + `scrollIntoView` on `[data-testid="message-${id}"]`) and the message DOM has the testid (`channel-client.tsx:791`), so it should work. A contract test that inserts a fake file via SQL and clicks the button would close the loop.
* **The Files tab is per-channel, not per-server.** The API call uses `?channelId=...` correctly, but the empty-state text says "No files in {currentTitle} yet" — which uses the channel title, not the server. This is correct UX.
* **The `Files` icon is shared between the tab and the empty-state card** — both use `lucide-react`'s `Files` icon. Mildly confusing visually but not a defect.
