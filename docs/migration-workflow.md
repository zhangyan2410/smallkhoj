# 数据库迁移工作流

SmallKhoj 以 Alembic revision 作为部署 schema 的唯一真相源。ORM 定义位于
`backend/models/slock.py`；`backend/models/seed.py` 只执行幂等数据种子和旧数据
回填，不创建、修改或删除表、索引、约束与扩展。

## 新数据库

在 `backend/` 下运行：

```bash
uv run alembic upgrade head
uv run uvicorn main:app --host 0.0.0.0 --port 8000
```

开发和生产 compose 的 backend 命令已固定为这个顺序。直接启动 uvicorn 时，
应用也会只读检查 `alembic_version`：revision 缺失、落后或不是当前唯一 head 时
会拒绝启动，并提示执行迁移；应用生命周期不会用 `create_all` 补表。

## 接管 Alembic 之前创建的旧数据库

旧库不能直接运行 baseline，也绝不能执行 `alembic stamp head`。前者会和已有
对象冲突；后者会把尚未执行的迁移伪装成已执行，可能跳过数据修复和 identity
高水位校准。

先停止写入并备份数据库，然后针对明确的目标 URL 运行只读指纹检查：

```bash
cd backend
DATABASE_URL='postgresql+asyncpg://…/目标库' \
  uv run python -m scripts.legacy_schema_preflight
```

该命令只读取表、列、索引、约束、`messages.seq` identity 状态和
`alembic_version` 是否存在，不写数据库。只有输出 `matches the read-only
baseline fingerprint`，且操作员核对目标库无误后，才依次执行：

```bash
uv run alembic stamp 77b8b147f689
uv run alembic upgrade head
```

stamp 的对象只能是 baseline revision `77b8b147f689`。指纹报告缺表、缺列、
缺索引、缺约束、已有 Alembic 状态或 `messages.seq` 已是 identity 时必须停止，
先调查漂移，不能强行 stamp。

## 日常 schema 变更

1. 先修改 `backend/models/slock.py`。
2. 运行 `uv run alembic revision --autogenerate -m "<说明>"`。
3. 人工审查生成的 upgrade/downgrade；autogenerate 不是可直接发布的答案。
4. 在独立一次性 PostgreSQL 数据库验证 `upgrade`、必要的 `downgrade`、再
   `upgrade`，以及历史数据迁移不变量。
5. 运行完整 backend 测试和迁移测试，再提交模型与 revision。

已经进入 `main` 或共享环境的 revision 不得原地改写；用新的 revision 修正。
破坏性 DDL 应设置合理的 `lock_timeout`，在无应用写入窗口执行，并准备针对
该 revision 的恢复步骤。

## `messages.seq` 迁移契约

- baseline 中 `messages.seq` 是历史普通 `BIGINT`；
- `0002_messages_seq` 添加 `GENERATED BY DEFAULT AS IDENTITY`，并在同一迁移
  事务和表锁内把 sequence 对齐到现有最大值；
- 过渡期仍允许旧 writer 显式写入；
- `0003_messages_seq_auto` 在最终切换前再次对齐高水位，并改为
  `GENERATED ALWAYS`；
- 当前 public API、agent API 和 reminder writer 都省略 `seq`，只由 PostgreSQL
  分配。回滚应用版本时，不得把旧的显式 writer 部署到 `GENERATED ALWAYS`
  schema 上。

真实回归测试位于 `backend/tests/test_alembic_migrations_postgres.py`。它要求显式
隔离的 admin/test URL，为每例创建唯一数据库并在 `finally` 删除；不得用共享库，
也不得用 `Base.metadata.create_all` 代替 revision 执行证据。
