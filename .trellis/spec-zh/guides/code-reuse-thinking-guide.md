# 代码复用思考指南

> **目的**：写新代码之前停下来想一想——它是不是已经存在？

---

## 问题所在

**重复代码是不一致性 bug 的头号来源。**

当你复制粘贴或重写已有逻辑时：
- bug 修复无法传播
- 行为随时间逐渐分叉
- 代码库变得更难理解

---

## 写新代码之前

### 第 1 步：先搜索

```bash
# Search for similar function names
grep -r "functionName" .

# Search for similar logic
grep -r "keyword" .
```

### 第 2 步：问自己这些问题

| 问题 | 如果是…… |
|----------|-----------|
| 已存在类似函数吗？ | 使用或扩展它 |
| 这个模式在别处用过吗？ | 遵循现有模式 |
| 它可以成为共享工具吗？ | 在正确的位置创建它 |
| 我正在从别的文件复制代码吗？ | **停下**——提取成共享代码 |

---

## 常见重复模式

### 模式 1：复制粘贴函数

**坏**：把一个校验函数复制到另一个文件

**好**：提取到共享工具，需要处导入

### 模式 2：相似组件

**坏**：新建一个与现有组件 80% 相似的组件

**好**：用 props/变体扩展现有组件

### 模式 3：重复常量

**坏**：在多个文件里定义同一个常量

**好**：单一事实来源，各处导入

---

## 何时抽象

**该抽象时**：
- 同一段代码出现 3 次以上
- 逻辑复杂到容易出 bug
- 多人可能需要它

**不该抽象时**：
- 只用一次
- 不起眼的单行代码
- 抽象比重复更复杂

---

## 批量修改之后

当你对多个文件做了类似改动后：

1. **复查**：所有实例都改到了吗？
2. **搜索**：跑一遍 grep 找漏网的
3. **考虑**：需要抽象吗？

---

## 陷阱：不对称的机制产出同一结果

**问题**：当两个不同机制必须产出同一组文件时（例如 init 用递归目录复制，update 用手工 `files.set()`），结构性改动（重命名、移动、新增子目录）只会经由自动机制传播，手工那份会静默漂移。

**症状**：init 完美运行，update 却把文件建在错误路径，或者干脆漏掉文件。

**预防检查清单（checklist）**：
- [ ] 迁移目录结构时，搜索所有引用旧结构的代码路径
- [ ] 如果一条路径是自动推导的（glob/复制）而另一条是手工列举的，手工那份需要更新
- [ ] 加一条比较两个机制输出的回归测试

---

## 提交前检查清单

- [ ] 已搜索过现有相似代码
- [ ] 没有本应共享却被复制粘贴的逻辑
- [ ] 常量只在一处定义
- [ ] 相似模式遵循相同结构
