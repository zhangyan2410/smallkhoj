## 7. `rtk test` 的正确定位：子命令误用，非工具假绿

> 2026-07-22 实测修正。前一稿（含旧 HANDOFF §5）把此事定性为
> “`rtk test` 假绿 / 包装层 bug”，这是错误的。实测真相如下。

`rtk test` 的真实语义是“**运行一个测试套件命令，只显示失败**”，参数是
要执行的测试命令（例如 `rtk test cargo test`、`rtk test pnpm test`）。
它**不是** shell 内建 `test` / `[` 的代理，也不做文件存在性检测。

计划 001 把它误当成文件检测：

```bash
rtk test ! -e <path>     # 误用
```

实测：`rtk test` 把 `!`、`-e`、`<path>` 当成“要跑的测试命令”，于是 shell
尝试执行名为 `-e` 的命令，输出 `sh: -e: command not found`。更关键的是，
`rtk test` 对子命令退出码有自己的处理逻辑——实测 `rtk test false` 仍返回 0，
`rtk test ! -e <path>` 无论文件存在与否都返回 0。

因此这不是“rtk 工具有 bug”，而是“计划作者误用了子命令”。**rtk 本身没坏。**

**实测的退出码语义对照（2026-07-22，合成路径）：**

```text
rtk test <args>   总是返回 0   （不透传；用于跑测试套件，非断言）
rtk run  <args>   总是返回 0   （不透传；sh -c raw 执行）
rtk proxy <args>  如实透传退出码   （可用于断言）
rtk zsh -c '<expr>'   zsh 内部 set -e 生效，退出码可靠
```

结论：

- 这是执行计划中的真实错误，但**不是 SmallKhoj 运行时的容量阻断项**；
- 修复方式：把 69 处 `rtk test` 误用改成 `rtk proxy test ...` 或
  `rtk zsh -c '[[ ... ]]'`；为彻底避免 `rtk` 输出截断干扰断言，优先用
  `rtk zsh -c '[[ ... ]]'`；
- 不要因此重新冻结全部计划、重算所有哈希或阻塞产品修复 PR。旧
  plan-freeze reviewer GO 与 ledger 建立在错误工具用法之上，已被推翻，
  只能作为历史记录，不能继续当发布凭证。
