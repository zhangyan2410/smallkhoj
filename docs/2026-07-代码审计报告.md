## 2026-07-23 已确认的高风险基线缺陷（历史 RED）

以下内容保留当时的失败机理和 RED 证据，便于追溯为什么必须整改。对应重要合同已在当前
本地候选实现并通过聚焦门禁，但仍受“最终全量门禁、提交、合并、部署未完成”的边界约束。

### 1. Alembic 与 `messages.seq` 仍不可安全部署

原始 finding 属实：应用曾使用 `max(seq)+1`，并发时会分配相同序号。把生成责任移到数据库
identity 的方向正确，但 advisor 迁移没有处理历史数据和过渡期 writer。

真实 PostgreSQL 16 探针执行：

```text
upgrade baseline
→ 显式插入 messages.seq=1,2,3
→ upgrade 0002_messages_seq
→ 省略 seq 插入下一条消息
```

结果：identity sequence 仍从 1 开始，第一条隐式插入报：

```text
duplicate key value violates unique constraint "messages_seq_key"
Key (seq)=(1) already exists
```

此外：

- `docs/migration-workflow.md` 的旧方案建议 `alembic stamp head`，会把未执行迁移标为已执行；
- 旧库已有表但没有 `alembic_version` 时，直接从 0001 upgrade 会撞已有表；
- FastAPI lifespan 仍调用 `create_tables()` / `Base.metadata.create_all`，会制造“schema 看似最新、
  迁移版本未知”的第三种状态。

正确终态应是：只读 legacy fingerprint/preflight → 只 stamp 已证明等价的 baseline revision →
upgrade head；迁移把 identity restart 到所有历史/显式值之上；应用启动不再执行隐式 DDL。

### 2. Task DELETE 真实事务会失败

advisor 009 的 fake-session 测试通过，但没有执行 PostgreSQL 外键。路由顺序是：

```text
DELETE tasks
→ INSERT activity_logs(task_id=刚删除的 UUID)
→ INSERT event_records(task_id=刚删除的 UUID)
```

真实 PostgreSQL 分别稳定命中：

```text
activity_logs_task_id_fkey
event_records_task_id_fkey
```

事务回滚后 Task 仍存在，activity/event 均为 0。`ON DELETE SET NULL` 只处理删除时已经存在
的引用，不允许删除后新插入一个指向不存在实体的 FK。

正确终态应先捕获 primitive tombstone，再删除依赖/实体，然后用 `task_id=NULL` 记录活动和
专用 `task.deleted` 事件，把旧 UUID 放在 details/payload 中，commit 后再 publish。

### 3. 鉴权和租户隔离未闭环

- 后端读取 `PUBLIC_API_KEY`，生产 compose/env/前端主要使用 `NEXT_PUBLIC_API_KEY`；自定义
  key 会导致前后端认证断裂。
- 默认 key 仍是仓库已知值；生产未配置不能安全回落。
- credential 仍通过 `?api_key=` 进入 URL，可能出现在代理日志、历史和诊断记录。
- 所谓 permission “default-deny”仍默认允许当前代码检查的全部权限，只拒绝未来未知字符串。
- actor 修复只接受裸 display name，合法 `@alice` 和 viewer UUID 被误判 403。
- first-user-wins 没有数据库并发约束，两个独立事务可各自观察零 membership 并提交两个 owner。
- 普通用户可创建 `server_id=NULL` 的全局 builtin；legacy NULL 行会被查询隐藏；slug 仍全局
  唯一，造成跨租户干扰和枚举风险。

这些问题必须作为一个跨 backend/frontend/compose/数据库的终端合同修复，不能只补单点测试。

### 4. 查询、分页和长连接仍有正确性问题

- `/search`、`/history` 中 reply count 仍可能每条消息单独查询；005 没有达到自己的 query-
  count 验收。
- 用 `None` 同时表达“已经预取且不存在”和“没有提供预取值”，会触发意外回查。
- agent `/events` 仍声明 `Depends(get_db)`；FastAPI yield dependency 会在 StreamingResponse
  完成后才退出，因此长流仍占住 session/事务。
- NOTIFY pool acquire/execute 失败后只记录并返回，没有恢复/重建策略。
- server-wide task 游标只用 `task_number`，但唯一键是 `(channel_id, task_number)`；跨 channel
  会重复或漏数据。
- `/threads` 先 limit roots、再在 Python 过滤无回复 root，可能返回空页，即使更老数据仍有
  合格 thread。
- 多个前端页面只请求第一页，不消费 `nextCursor`，第 51 条以前的数据会从 UI 消失。
- 页面可能挂载两个 `RealtimeRefresh`，形成两条 SSE；task targeted refresh 不等于所有页面
  refresh 已被消除。

### 5. CI 与 e2e 不能作为发布门禁

019 中新增脚本本身可运行，但按提交的 workflow：

- `uv run ruff check .` 当前报告 73 个错误；
- `bun run build` 没有 Better Auth/bridge/public-key 所需的非敏感 CI env，会在 production build
  阶段失败。

023 的管理流程没有登录或注入有效 session，也没有 active server/account context；受保护页面
会跳 `/login`。测试还硬编码 `sk_public_local`。因此不能直接把它声明为 canonical e2e。

仓库可见 UI 验收必须使用项目 `./twd` wrapper，并在隔离 worktree runtime 上记录 CWD、分支、
URL、DOM/network/trace markers。已有 advisor 分支没有这些证据。
