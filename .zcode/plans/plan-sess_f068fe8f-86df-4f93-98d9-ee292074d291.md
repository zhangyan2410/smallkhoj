## 诊断：为什么 ZCode 拿不到 Codex 沉淀的上下文

切到 ZCode 后效率受影响，根因是两层独立的"上下文断裂"：

**M1（主因·每次提问都是裸的）** — Codex 靠 `.codex/hooks/hooks.json` → `.codex/hooks/inject-workflow-state.py`，在每次 prompt 注入一段 `<workflow-state>` 面包屑（当前 Trellis active task、状态、workflow 提示）。ZCode 客户端其实支持同样的 `UserPromptSubmit` hook 且输出 schema 兼容，但：
- 项目里没有 `.zcode/config.json`（workspace scope 缺失）；
- `~/.zcode/v2/config.json` 的 `hooks: {}` 为空，且未设 `hooks.enabled: true`（配置型 hook 默认禁用）；
- `trellis init` 对 zcode 平台标 `hasHooks:false`，不会自动 wiring。

结果：在 ZCode 里每个提问都看不到当前任务/进度，必须手动重讲背景 —— 这正是"获取不到 codex 上下文"的主因。

**M2（次因·跨工具回顾缺失）** — `trellis mem` 不识别 `zcode` 平台（`unknown platform: zcode`），ZCode 会话存于 `~/.zcode/cli/db/db.sqlite` + `model-io-*.jsonl`，格式与 Codex rollout 不同，无法被检索。反过来，ZCode 里的 AI 默认也不会主动调 `trellis mem search --platform codex` 去捞 Codex 沉淀。

关键利好（已验证）：ZCode 运行 hook 时会注入 `${CLAUDE_SESSION_ID}` / `${CLAUDE_PROJECT_DIR}`（复用 Claude 名），所以**已有的 hook 脚本会以 "claude" 身份运行，天然拿到 session-scoped 的 active task 隔离，零改动**；hook 输出也正好符合 ZCode 的 strict JSON schema。

## 实施方案（分层，核心改动零代码风险）

### 第 1 步【核心·必做】新建 ZCode workspace hook 配置
新建 `/Users/code/project/smallkhoj/.zcode/config.json`：
```json
{
  "hooks": {
    "enabled": true,
    "events": {
      "UserPromptSubmit": [
        { "hooks": [
          { "type": "command",
            "command": "python3 -X utf8 \"${ZCODE_PROJECT_DIR}/.codex/hooks/inject-workflow-state.py\"",
            "timeout": 15,
            "statusMessage": "Loading Trellis task context" }
        ] }
      ]
    }
  }
}
```
- 复用已有 `.codex/hooks/inject-workflow-state.py`，**不新建脚本、不改脚本**。
- workspace scope 可随 git 共享，团队成员用 ZCode 时自动生效。
- 预期效果：在 ZCode 提问即自动带上当前 active task 的 `<workflow-state>`，与 Codex 体验一致。

### 第 2 步【必做】验证 hook 真实生效
- 离线喂数据：`echo '{"cwd":"/Users/code/project/smallkhoj"}' | python3 -X utf8 .codex/hooks/inject-workflow-state.py`，确认输出合法 JSON 且含 `<workflow-state>`。
- 在 ZCode 新开会话提问，用 `./smallkhoj-trace` 或查 ZCode log 确认 hook run 记录（outcome=success、有 additionalContext 注入）。
- 若 session 隔离退化（多窗口串任务），再进第 3 步。

### 第 3 步【可选·语义增强】显式让 Trellis 识别 zcode 平台
小改项目本地脚本（非第三方包，风险低）：
- `.trellis/scripts/common/active_task.py`：`_KNOWN_PLATFORMS` 加 `"zcode"`；`_ENV_SESSION_KEYS` 加 `("zcode", ("ZCODE_SESSION_ID","CLAUDE_SESSION_ID"))`。
- `.codex/hooks/inject-workflow-state.py` 的 `_detect_platform` env_map 加 `"ZCODE_PROJECT_DIR": "zcode"`（**放在 `CLAUDE_PROJECT_DIR` 之前**，避免被 claude 抢先识别）。
- 收益：平台身份正确、多工具并行时 session 隔离语义清晰。
- ⚠️ 注意：若未来 `trellis init` 同步覆盖这些脚本，本地改动会丢失 → 需在 `.trellis/spec/` 记一笔或提上游。

### 第 4 步【可选·工作流补充】让 ZCode 主动回顾 Codex 历史
- 在 `AGENTS.md` Project Index 段或新建 `.trellis/spec/cross-tool-context.md` 加规则："当用户提到'之前/上次/上次怎么解的/之前讨论过'，优先 `trellis mem search "<关键词>" --platform codex --cwd <repo>` 检索 Codex 沉淀。"
- 复用已有 `trellis-session-insight` skill。解决 M2 的"主动获取"侧，零平台代码改动。

### 不在本次范围
让 `trellis mem` 原生支持 zcode 平台（需改第三方包 `@mindfoldhq/trellis`，新增 ZCode sqlite/jsonl reader）—— 成本高、升级易冲突，留作后续议题。

---

**执行顺序**：第 1 步 → 第 2 步（验证通过即解决主痛点）→ 按需决定第 3、4 步。

需要 Bash 权限用于：运行 hook 做离线验证、调用 `trellis mem`/`smallkhoj-trace` 核对生效。
