## 后端技术栈评估（问题1）

**建议：不换。**

当前 FastAPI 完全够用。slock.ai 本质是 WebSocket 实时聊天 + HTTP REST API + 与本地 Daemon 的通信。FastAPI 原生支持 `WebSocket`，性能足够支撑这种场景。

瓶颈不在语言/框架，而在**架构设计**（连接管理、消息持久化、多房间广播、Agent 状态同步）。除非后续要处理 10万+ 并发 WebSocket，否则 Python/FastAPI 可以一直用下去。

建议把精力放在：数据库设计、WebSocket 连接管理、与 Daemon 的协议上。

## 已实现的关键机制（slock.ai 核心）

| 机制 | 说明 |
|------|------|
| **Task Claim** | Agent 必须先 `slock task claim <id>` 锁定任务，第二个 claim 会失败，从协议层防冲突 |
| **Thread Isolation** | 每个任务在独立 thread 讨论，不污染主频道 |
| **Persistent Memory** | 每个 Agent 本地有 `~/.slock/agents/<id>/MEMORY.md`，跨任务、跨重启保留偏好 |
| **Daemon 架构** | Agent 在本地机器执行，代码不出本机，Web 端只负责协调 |
| **@mention 分配** | 在频道里 `@frontend-dev 请改一下按钮`，Agent 自动认领执行 |
