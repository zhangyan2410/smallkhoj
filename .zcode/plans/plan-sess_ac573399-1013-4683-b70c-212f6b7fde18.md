# 切换页面"加载工作台"闪烁 — 根治方案（按 Trellis 流程留痕）

## 问题根源（一句话）

`ProductShell`（含 icon 导航栏 + WebGL 水墨画布 `AppDeskBackground` + 引擎脚本）**被每个页面各自渲染**，没有放在共享 layout 里。每次路由切换 → 整个外壳拆掉重建（WebGL 初始化是大头）→ 肉眼可见的"咯噔"。项目**没有任何 `loading.tsx`**，连过渡兜底都没有。

> 关键证据：spec 自己写着「icon rail: one source, in ProductShell」，且 `test/inkframe-object-ui.test.tsx` 断言 `AppDeskBackground`/`InkMaterialRuntimeScript` 在 `product-shell.tsx` 里恰好各一次。所以这次必须走 Trellis 留痕 + 更新 spec，否则 spec 与代码会打架。

**1.1 规划产物**（我会写满 3 个文件，符合"complex task"要求）

- **`prd.md`** — 需求/验收标准/停止条件：
  - 需求 P1：外壳 chrome（rail + 背景 + 引擎）跨路由只挂载一次，切页不再重建。
  - 需求 P2：realtime-refresh 的 `router.refresh()` 不再触发整页外壳重绘（改用局部/缓存友好的刷新）。
  - 需求 P3：icon 导航高亮按当前路由派生（原来靠每页传 `active` prop）。
  - 需求 P4：`/login`、`/join/[token]` 公开路由不受影响（不挂外壳、不需登录）。
  - 验收：切页肉眼无外壳重建；`./twd` 录证；lint/typecheck/test 全绿；测试断言更新后通过。
  - 停止条件：若路由组改造牵连到 auth 流程回归，停下来重新评估。

- **`design.md`** — 技术设计：
  - **路由组方案**：新增 `app/(app)/layout.tsx` 作为「已登录外壳」layout，把 `InkMaterialRuntimeScript` + `AppDeskBackground` + icon rail 移到这里，调一次 `requireCurrentAccount()`。把 `/`、`/chat`、`/tasks`、`/members`、`/computers`、`/settings`、`/control`、`/daemon`、`/dm` 移进 `(app)` 路由组；`/login`、`/join/[token]` 留在顶层。
  - **rail 改为路由派生**：抽出一个 client 子组件 `AppRail`（用 `usePathname()` 算 active），`ServerSwitcher` 已是 client、已用 `usePathname`，有先例。
  - **`ProductShell` 瘦身**：移除 `InkMaterialRuntimeScript`、`AppDeskBackground`、icon rail、`getTranslations("nav")`、`session` prop（这些上移了）。保留 `ProductShellBody`（header title/description/actions + 三栏 body）。各页面只传 `title`/`description`/`actions`/`list`/`listConfig`/`sidebar`/`className`/`mainScrollable`/`children`。
  - **chat layout 特殊处理**：`app/chat/layout.tsx` 保留 `ChatDataProvider` + 4 个 fetch + `<ChatSidebar/>` 作为 list 内容；不再渲染外壳 chrome（已在 (app) layout）。channel 切换本就不重渲 chat layout，继续保持。
  - **`router.refresh()` 策略**：realtime-refresh 仍保留全页 `router.refresh()`（Next 里这是刷新当前路由 server 组件，不会重建 (app) layout 的 chrome，正好达到目的）。评估改用 `router.refresh()` + `unstable_cache` 标签 / 局部 revalidate，减少抓取量；列为 P2 可选项，不阻塞验收。
  - **WebGL 单例不变**：`materialSurfaceCoordinator` 按 `(region, ownerId)` 去重，移到根 layout 后仍是单实例，不会双挂载（前提：必须从 `product-shell.tsx` 删除这些渲染，否则会双挂载冲突）。
  - **层叠风险**：`.sk-workbench-desk` 有不透明 `--paper` 背景色，背景层 `position:fixed z-0`、内容 `z-10`；移动后用 `./twd` 实测背景仍可见。

- **`implement.md`** — 有序执行清单 + 验证命令 + 回滚点。

## 两个实现关键决策（影响范围大，我想先对齐）

这两点会改变改动量和最终形态，所以我用问题形式问你（在 ExitPlanMode 后会弹出）：

1. **路由组 vs 条件渲染**：用 `app/(app)/layout.tsx` 路由组（推荐，Next 原生，URL 不变，干净），还是在现有 `app/layout.tsx` 里按路径条件渲染外壳（改动小但 hacky）。
2. **realtime-refresh 处理深度**：外壳持久化后 `router.refresh()` 闪烁基本消失，是否还要深入改刷新策略（加 cache tag/局部 revalidate）。

## 风险与回滚
- 风险：移动文件到路由组若 import 路径/相对引用出错 → typecheck 会立刻抓住。
- 回滚：全部改动集中在新增 layout + 移动文件 + `product-shell.tsx` 瘦身，`git checkout` 即可整体回退。
- 不破坏 chat channel 切换的 layout 持久性（App Router layout 跨动态段本就持久）。
